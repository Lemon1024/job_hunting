# 移动端投递工作台 v0.2

> 状态：已批准  
> 批准日期：2026-07-25  
> 主要平台：移动端；地址与待办能力要求桌面端完整一致

## Problem Statement

如何让个人求职者在移动端完成“识别求职漏斗、快速筛选、维护申请、安排后续行动和确认账号状态”的完整闭环，同时保持桌面端与 Supabase 数据语义一致？

当前移动端存在六个相互关联的问题：顶部指标卡使用错误的筛选条件；申请无法删除；地址只能单选且不能复用自定义标签；“我的”页错误显示未登录且入口没有真实行为；日历无法维护多个待跟进事项；招聘流程缺少主管面。

## Recommended Direction

建设一个以“下一步行动”为中心的双端投递工作台：移动端负责高频维护体验，桌面端完整支持共享的多地址与多待办数据。顶部指标、筛选结果和统计必须来自同一组共享谓词；地址和待办升级为受 RLS 保护的独立实体；账号中心只保留有真实行为的入口。

这不是开放式 CRM。招聘状态仍由产品控制，只新增 `manager`；待办保持全天日期，不增加时间点、循环和指派；提醒只在应用内呈现，不引入系统或服务端推送。

## Key Assumptions to Validate

- [ ] 多地址需要跨申请复用、重命名和跨端同步，而不是普通字符串数组。
- [ ] 一条申请需要多个独立待办，而不是一个 `next_action_date`。
- [ ] 固定新增主管面足以表达当前招聘流程，不需要任意自定义状态。
- [ ] 应用内即将到期/逾期提醒可以满足当前使用需求。
- [ ] 深色主题和设置中心的使用价值足以覆盖全移动端主题改造成本。

## MVP Scope

- 顶部四项按“待投递、总投递、面试中、Offer”排列，默认总投递。
- `todo` 单独计入待投递；总投递排除 `todo`；面试覆盖一面、二面、三面、主管面和 HR 面。
- 移动端申请详情支持编辑和带确认的永久删除。
- 用户级地址标签库，申请可多选地址，双端完整增删改查和任意匹配筛选。
- 多条跟进任务，双端完整增删改查、完成/恢复、日历与应用内提醒。
- 新增固定状态 `manager`，位于 `interview3` 与 `hr` 之间。
- 设置中心支持昵称、私有头像、只读邮箱、修改密码、主题、应用内提醒偏好、关于、帮助、邮件反馈和退出。
- 反馈调用系统邮件，收件地址为 `418154155@qq.com`。
- 迁移旧 `city` 与 `next_action_date` 数据，同时保留旧列至少一个兼容版本。

## Not Doing

- 不实现系统本地通知或 Expo 服务端推送。
- 不开放任意自定义招聘状态。
- 不实现循环任务、子任务、时间点提醒或任务指派。
- 不实现团队共享地址标签。
- 不修改登录邮箱，也不建设应用内反馈后台。
- 不实现离线写入队列和跨设备冲突合并。
- 不立即删除旧 `city` 与 `next_action_date` 字段。

## Decisions

- 地址标签：用户级规范化标签表与申请关联表；单标签最长 32 字符，一条申请最多 10 个。
- 多地址筛选：命中任意一个所选标签。
- 待办：标题与日期必填，备注可选，`completed_at` 表示完成状态。
- 提醒：应用内显示即将到期和已逾期；提前天数支持 0、1、3、7 天。
- 主题：跟随系统、浅色、深色；默认跟随系统。
- 头像：Supabase Storage 私有 bucket，用户只能访问自己的对象。
- 删除：申请永久删除并级联事件、地址关联和待办；地址标签本身保留。
- 桌面端：地址和待办与移动端完整一致；设置中心仍以移动端为主。
